EL PROBLEMA

137 tools sin comunicación

Hoy las tools existen como catálogo (tools.json) pero ninguna ejecuta nada cuando otra produce un evento. El sistema es un logger ISO con dashboard, no una plataforma colaborativa.

Lo que ya funciona ✓

• Ingesta de eventos vía POST /api/v1/events
• Validación AJV contra event-standard.json
• Persistencia en industrial_events
• Dashboard con KPIs
• Reporte ISO con 10 normas
• Catálogo de 137 tools y reglas de comunicación

Lo que falta ✗

• Ejecutor que active la regla de communication-rules.json
• Handlers reales por cada tool
• Trazabilidad de cadenas causales (correlation_id)
• Cola de errores (dead-letter)
• Fan-out automático tool→tools

LA DECISIÓN

Push In-Process

Hay dos ejes independientes: cómo se entera una tool de un evento (pull / push), y dónde vive el código (microservicio / in-process). Elegimos push + in-process.

MicroservicioIn-process ✓
Pulltool consulta API por HTTPworker consulta DB y llama función
Push ✓API hace POST a URL de la toolbus llama handler directamente

✓ Sin red

Microsegundos de latencia. No hay HTTP, ni colas, ni auth entre tools.

✓ Sin 137 deploys

Una sola aplicación Node. Cada tool es un archivo, no un servicio.

✓ Trazabilidad

Toda la cadena causal vive en el mismo log y la misma tabla.

LAS 3 PIEZAS NUEVAS

toolRunner · eventBus · handlers

Todo lo demás ya existe. Solo construimos estas tres cosas para cerrar el círculo.

1. toolRunner

Carga todos los archivos de src/tools/ al arrancar. Expone runTool(id, evento) que invoca el handler correspondiente. Una sola pieza, no le importa qué hace cada tool.

2. eventBus

Worker que lee eventos nuevos de industrial_events, los cruza con communication-rules.json, y llama al toolRunner para cada tool que debe reaccionar. Propaga correlation_id.

3. handlers

Un archivo src/tools/<tool_id>.js por tool. Exporta meta y handler. La función recibe un evento, devuelve otro evento (o null). 137 archivos.

// src/services/toolRunner.js — esencia import { readdirSync } from 'fs'; const tools = {}; for (const file of readdirSync('./src/tools')) { const mod = await import(`./tools/${file}`); tools[mod.meta.id] = mod; } export async function runTool(toolId, inputEvent) { const tool = tools[toolId]; if (!tool) throw new Error(`Tool desconocida: ${toolId}`); return await tool.handler(inputEvent); }
ANATOMÍA DE UN HANDLER

Cómo se ve una tool real

Un archivo, dos exports: meta (describe la tool) y handler (la ejecuta). Sin clases, sin frameworks, sin red.

// src/tools/detect_production_deviation.js export const meta = { id: 'detect_production_deviation', version: '1.0.0', consumes: ['PRODUCTION_METRICS_SNAPSHOT'], produces: ['PRODUCTION_DEVIATION_DETECTED'], category: 'productivity', description: 'Compara planificado vs real y emite alerta.', }; export async function handler(inputEvent) { const { planned, actual } = inputEvent.data; const deviationPct = ((actual - planned) / planned) * 100; if (Math.abs(deviationPct) < 5) return null; // nada que emitir return { event: { type: 'PRODUCTION_DEVIATION_DETECTED', category: 'productivity', severity: Math.abs(deviationPct) > 15 ? 'high' : 'medium', }, asset: inputEvent.asset, data: { planned, actual, deviation_pct: deviationPct }, }; }

El bus rellena automáticamente event_id, timestamp, module, correlation_id y causation_id. El handler solo se ocupa de la lógica.

REGLAS DE COMUNICACIÓN

communication-rules.json

Una regla declara: cuando la tool X emite el evento Y, dispara la tool Z (opcionalmente bajo cierta condición).

{ "id": "rule-prod-014", "sourceToolId": "production_metrics_collector", "targetToolId": "detect_production_deviation", "event": "PRODUCTION_METRICS_SNAPSHOT", "protocol": "internal", "topic": "tool/detect_production_deviation", "triggerCondition": "data.planned > 0", "description": "Las métricas alimentan al detector de desviación." }

Fan-out

Una source, varias targets → 3 reglas con misma sourceToolId y event, distintos targetToolId.

Fan-in

Varias sources, una target → N reglas con distintos sourceToolId, mismo targetToolId.

Cadena

A→B→C→D → N-1 reglas, una por par consecutivo. El correlation_id se propaga.

ESTRATEGIA DE ARRANQUE

137 placeholders primero

Antes de escribir lógica real, generamos los 137 archivos con un handler "tonto" que devuelve datos plausibles. Resultado: el flujo end-to-end funciona desde el día 1.

Por qué hacerlo así

• Demo completo desde el primer commit.
• Dashboard se llena.
• Reporte ISO se genera.
• Las cadenas tool→tool se ven funcionar.
• Reemplazas un placeholder por lógica real sin romper a nadie.

Reglas de un placeholder

• meta.version = 0.x.x-placeholder
• description empieza con [PLACEHOLDER]
• Salida incluye data._placeholder: true
• Valores plausibles, no null ni "TODO"

// Versión placeholder · misma forma exacta · valores fake export async function handler(inputEvent) { return { event: { type: 'PRODUCTION_DEVIATION_DETECTED', category: 'productivity', severity: 'medium' }, asset: inputEvent.asset, data: { deviation_pct: 8.4, _placeholder: true }, }; }

Roadmap de implementación

Normalizar communication-rules.json

Mantener todos los event en SCREAMING_SNAKE_CASE (PRODUCTION_METRICS_SNAPSHOT), añadir protocol: "internal" donde aplique.

Añadir campos al modelo de evento

Migración SQL: correlation_id, causation_id, processed_at en industrial_events. Sin tocar columnas existentes.

Construir toolRunner.js

Carga dinámica de src/tools/*.js. Una función pública: runTool(id, evento).

Generar 137 placeholders

Script que lee tools.json y crea un archivo por tool. Todos con el mismo esqueleto, valores fake.

Construir eventBus.js

Worker (setInterval 1s o LISTEN/NOTIFY) que dispara las reglas. Try/catch por handler, dead-letter en errores.

Endpoint /events/chain/:correlation_id

Devuelve la cadena causal completa. Herramienta de debug y showcase para el demo.

Implementar 3–5 handlers reales

Los más visibles para el demo: detect_production_deviation, predict_demand, iso_10816_engine. El resto sigue placeholder.

Validación contra event-standard.json

El AJV debe rechazar eventos que no cumplan. Schema por event.type, no solo por estructura base.
